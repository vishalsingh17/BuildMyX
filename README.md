# BuildMyX

Next.js 16, React 19, TypeScript and Tailwind CSS 4. A conversion-focused website for reporting/AI development, practical learning and developer sourcing, with a real sample-data workflow and a server-side enquiry endpoint.

## Run and deploy

```sh
npm ci
cp .env.example .env.local
npm run dev
```

For production, set the hosting environment variables, then run `npm run build` and `npm start`, or deploy with a Next.js-compatible Node/Vercel host. **A static-only host cannot run the enquiry endpoint.** The application uses Next's standalone output; if packaging `.next/standalone` yourself, also copy `public` and `.next/static` into the corresponding standalone directories. `npm start` serves the regular production build.

Public settings are read at build time; rebuild when changing `NEXT_PUBLIC_*`. Email credentials belong in the chosen Convex deployment’s environment settings. Never commit `.env.local` or put a delivery key in a public variable.

## Development and production releases

Work on `dev`; production stays on `main`. Development must pass the automated checks and its Vercel preview build before the owner reviews and manually merges a `dev` → `main` release PR. That merge is the green flag. The deployment build validates the environment’s Convex key, builds the website, deploys the matching backend, then lets Vercel publish the website. Both use the same source. After a successful production deployment, development fast-forwards to the released commit if it has no newer work.

See [environment setup and release instructions](docs/environments-and-releases.md) for the required GitHub branch protection and separate Vercel deployment keys. Those account settings must be activated; adding workflow files alone does not enforce the gate. `npm run release:check` verifies branch protection. No release is auto-merged and database records or secrets are not synchronized between environments.

## Python, pandas, PyTorch and system design learning library

The `/learn/` section is generated by **Zensical 0.1.1**, installed in the ignored project-local `.venv`. Python **3.12 or newer**, including `venv` and `pip`, is required on build machines; the Python course uses 3.12 type-alias syntax. Documentation dependencies are pinned in `learning/requirements.txt`; the setup script installs them when that file changes. The optional PyTorch execution environment has its own pinned requirements. Nothing is installed globally.

```sh
npm run setup:learn       # create the Python environment and install dependencies
npm run build:learn       # generate /learn/ for the Next.js server
npm run dev:learn         # Zensical live preview on port 8000 (POSIX shell)
npm run test:pytorch      # install the pinned CPU runtime and execute the PyTorch chapters
```

`npm run dev` builds the lessons before starting Next. After editing lesson content, rerun `npm run build:learn`, or use the separate live preview. `npm run build` and the guarded Vercel build generate lessons before building Next and deploying the matching backend; a failed lesson build stops the release. `public/learn/` and the temporary build configuration are generated and never committed.

Edit `learning/content/**/*.md`, `learning/content/stylesheets/learning.css` and `learning/overrides/`. Navigation and theme settings live in `zensical.toml`. Add new page paths to `lib/learning.ts` as well, so Next serves the directory indexes and includes them in the production sitemap. Unknown lesson paths return a real 404. Canonical URLs follow `NEXT_PUBLIC_SITE_URL`; development and preview lessons have `noindex, nofollow` metadata. Zensical's search runs in the browser without a search service. The lessons do not collect analytics or store reading progress.

The marketing site's Learn links open a labelled new tab so an in-memory enquiry draft stays open in the original tab. The landing section links directly to Python, pandas and PyTorch as well as the library. Course tabs separate those three subjects and system design. The existing six system design lessons keep their URLs; their overview is now `/learn/system-design/`. The reading layout was inspired by the supplied System Design School reference; its articles, branding and paid content are not copied.

`/learn/python/` introduces fifteen original chapters, 101 Python code blocks, self-check questions and a public topic-coverage index. `learning/python-reference-topics.json` records all 160 headings from the requested Aman.ai primer and supplementary API-table terms, the source URL, capture date and HTML checksum. `learning/python-topic-map.json` maps every heading to a local chapter fragment. The fetched article itself is not copied into the repository.

`scripts/check-python-content.py` checks this inventory, public coverage links and required API terms. It compiles the teaching blocks and runs each chapter's examples in a separate Python process inside a temporary folder, with synthetic input, an execution timeout and no inherited application credentials. Labelled module examples become temporary fixture files. After Zensical builds, the checker validates the actual generated topic anchors and table terms. Both phases run automatically in `npm run build:learn`, so missing topics, broken mapped anchors or failed examples stop local, CI and Vercel builds. The lessons display code for readers to run locally; the website does not execute reader-supplied code or save exercise answers.

`/learn/pandas/` adds fifteen original chapters covering all **117 headings** in the requested [pandas primer](https://aman.ai/primers/pandas/), a downloadable synthetic workshop dataset, a complete reporting project, plotting and self-checks. The source snapshot and mappings are `learning/pandas-reference-topics.json` and `learning/pandas-topic-map.json`; the public index is `/learn/pandas/coverage/`. Version-sensitive topics explicitly use pandas **3.1.1**, including Copy-on-Write, current fill/frequency APIs and correct Series/DataFrame method names. NumPy, matplotlib, lxml, openpyxl and their dependencies are pinned alongside Zensical; they support the actual runnable lessons and optional I/O examples.

`scripts/check-pandas-content.py` validates all mappings and supplementary API terms before and after rendering. It compiles every teaching block and executes each chapter in a temporary directory with no application credentials, a simulated clipboard and non-interactive plots. It checks that the project fixture matches the downloadable CSV and that the CSV and original SVG chart are published unchanged. These checks run automatically with `build:learn`. Browser checks cover every lesson's layout, course navigation, actual pandas search results and the sample/figure assets alongside the existing website flows.

`/learn/pytorch/` has twenty original chapters, **101 core Python blocks**, five explicitly optional integration recipes and a coverage index for all **252 rendered headings** in the requested [PyTorch primer](https://aman.ai/primers/pytorch/). It includes vision/text/audio preprocessing, CNNs/LSTMs, masked loss, training, LoRA, experiments, metrics, export, serving, optimization, monitoring and Prefect/Airflow orchestration. Complete synthetic vision/text projects and workflow files can be downloaded in a ZIP; the source does not claim CIFAR-10 or IMDb benchmark performance. Its inventory, source checksum and mappings are in `learning/pytorch-reference-topics.json` and `learning/pytorch-topic-map.json`.

Normal website builds run `scripts/check-pytorch-content.py` to check coverage, supplementary API topics, all Python syntax and the source bundle, then verify the rendered anchors/assets. They **do not install a training runtime into the web host**. `npm run test:pytorch` additionally installs `learning/requirements-pytorch.txt` into the ignored `.venv` and executes all twenty trusted core chapter programs on the pinned CPU environment, in temporary directories with no application credentials. Linux x86-64 uses the explicit official PyTorch CPU wheels; compatible base versions are selected for other platforms. The examples test local FastAPI clients, offline experiment logging, ONNX output parity and complete training/artifact/prediction workflows. CI requires this execution check alongside the existing checks.

Blocks titled `Optional` are compiled but require their separately documented dataset/runtime: CIFAR-10, IMDb, TorchAO, Prefect 3 or Airflow 3. GPU execution and live orchestration/cloud integrations are not claimed as tested. To change downloadable project files, edit their labelled `# file:` teaching blocks and run `python3 scripts/package-pytorch-projects.py`; checks reject a stale ZIP. The original experiment SVG is committed as a teaching asset. Browser checks cover all **64 learning pages**, including actual PyTorch search, the source download, plot and draft-preserving landing entry.

## Enquiry storage and owner notifications

The built-in Next.js endpoint proxies submissions to the configured Convex HTTP actions URL. The live Vercel production site defaults to the [production deployment `kindhearted-hippopotamus-469`](https://dashboard.convex.dev/t/vishal-singh-6dda1/buildmyx/kindhearted-hippopotamus-469), using `https://kindhearted-hippopotamus-469.convex.site`. It also migrates the original development URL to this production endpoint when running on Vercel production. No Vercel email key is required. To select another backend, set `ENQUIRY_CONVEX_SITE_URL` to its `https://…convex.site` URL. Local development and Vercel previews default to `tacit-badger-38`; a development runtime refuses the known production URL. The deployment build supplies matching public URLs automatically. Set `ENQUIRY_ENABLED=false` on the Next.js server to force the copy-only fallback during maintenance or browser tests.

`GET /api/enquiry` checks database availability independently of email settings. `POST /api/enquiry` validates origin, JSON media type, a streamed 12 KB limit and all fields before forwarding. The Convex HTTP action repeats validation and applies shared limits: five new enquiries per normalized email address per ten-minute window and 200 requests using new references per day across the deployment. Only email hashes are used as rate-limit keys. Adjust the named limits in `convex/enquiries.ts` as traffic grows.

A random reference is bound atomically to a fingerprint of the normalized fields. Unchanged retries return the saved result without inserting another record or queuing a second notification; changed fields with the same reference return 409. The success response is `{ saved: true, reference }`. Network uncertainty keeps the draft and its original reference available for retry. Submitted fields and notification status are removed after 30 days by scheduled cleanup. Finalized email copies in the component are cleaned after seven days; abandoned copies after 30 days. Business inbox and provider retention settings are separate.

View submitted enquiries in **Convex dashboard → the matching deployment → Data → enquiries**. Enquiry fields, reference, notification status and any generic notification error appear there. There is no publicly accessible enquiry list or lookup. For administrator deletion, run the internal `enquiries:remove` mutation with the document’s `enquiryId`; it also cancels a queued notification when possible.

Owner emails require a Resend account; database storage does not. To activate notifications:

1. Create an account at [Resend](https://resend.com/signup), add a domain you own and complete [domain verification](https://resend.com/docs/dashboard/domains/introduction). A Gmail recipient is fine; the sender must belong to your verified domain.
2. In the **chosen Convex deployment’s** Settings → Environment Variables, add `RESEND_API_KEY`, `ENQUIRY_FROM` (for example, `BuildMyX <enquiries@your-domain>`), `ENQUIRY_TO` (your private notification address), and `ENQUIRY_EMAIL_TEST_MODE=false`. These belong in Convex, not in public browser variables. Never share keys in chat or commit them.
3. Optionally create a Resend webhook for `https://<deployment>.convex.site/resend-webhook`, enable all email events and store its `RESEND_WEBHOOK_SECRET` in that Convex deployment. Signature verification is handled by the Resend component. Without a webhook, API send status still updates, but final inbox delivery cannot be confirmed.
4. Submit a controlled enquiry and check both the `enquiries` row and your inbox. Existing unconfigured enquiries still inside the 30-day retention window are queued automatically within five minutes after settings become available.

Notifications use the visitor’s address as Reply-To and a stable idempotency key. Enqueue failures retry up to five times; transient delivery retries are managed by the component. A failed notification leaves the enquiry saved and visible to the owner. `queued`, `sent` and `delivered` are distinct states; `sent` does not guarantee final inbox delivery. No visitor receipt is promised by the database flow. Keep `ENQUIRY_EMAIL_TEST_MODE=true` in development and use Resend test recipients to avoid real email during tests.

All enquiry CTAs share one in-memory draft. The copy-only fallback remains available when storage is not configured. Capability checks time out after eight seconds and can retry; clipboard permission times out after fifteen seconds into manual copying. Refresh starts a new draft; no browser storage is used. An optional `NEXT_PUBLIC_ENQUIRY_ENDPOINT` can supply an external HTTPS intake instead; it must return `{ saved: true, reference }` or the supported legacy `{ delivered: true, reference?, confirmationSent }` contract and implement its own validation, limits and CORS.

## PostHog analytics and sales follow-up

PostHog is integrated through the official `posthog-js` SDK. The owner-supplied public browser token and US ingestion host are configured in `lib/site-config.ts`, so the Git-connected Vercel deployment does not depend on an untracked `.env.local`. These are public browser settings, not personal API keys or email credentials. Set `NEXT_PUBLIC_ANALYTICS_ENABLED=false` and rebuild to disable external analytics. Optional `NEXT_PUBLIC_POSTHOG_PROJECT_TOKEN` and `NEXT_PUBLIC_POSTHOG_HOST` values override the defaults. See [the PostHog setup guide](docs/posthog-setup.md) for dashboard and deployment steps.

The SDK loads only when configured and the visitor has not enabled Do Not Track or Global Privacy Control. The existing event hooks feed PostHog directly; no collector adapter is needed. Automatic interaction capture, replay, surveys, exception capture, feature flags and external extension loading are disabled. A final event guard strips SDK URL/referrer defaults, form data, person properties and unapproved events. Clean page views appear as `$pageview`. Service views, CTA clicks, enquiry starts/submissions/copies, bookings, demo runs and downloads retain their existing names.

Anonymous identifiers are held in tab memory to connect actions within the open visit. Cookies, local storage, session storage, person profiles and IP enrichment are disabled. Refresh starts a new visit, so unique visitor and returning-user figures are deliberately limited. Do not enable extra collection without reviewing the configuration and updating the public privacy page.

`NEXT_PUBLIC_ANALYTICS_ENDPOINT` remains an optional alternative collector. Setting it suppresses the default PostHog project unless an explicit PostHog token override is also supplied. It accepts the documented JSON event/path/label payload without visitor identifiers. Do not put a PostHog ingestion URL into that setting: its protocol is different. PostHog takes precedence when both its settings are supplied, avoiding duplicate collection. Setting `NEXT_PUBLIC_ANALYTICS_ENABLED=false` prevents both integrations from sending events. The local `buildmyx:analytics` CustomEvent remains available for inspection.

Use a private copy of `docs/lead-tracker-template.csv` to record qualified enquiries, follow-ups and actual won/lost outcomes. Do not put customer records in this public repository.
